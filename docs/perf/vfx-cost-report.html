Executive Summary
The tail (p95–p99 ~25–54ms) is dominated by concurrent WAAPI animation count, which hits 120–154 active element.animate() instances during heavy combat — the game janks even when particles=0 / impacts=0. The Canvas2D FX engine (particles, impacts, trails) is lean by design (no shadowBlur, pre-baked glows), but CSS drop-shadow/box-shadow/blur filters run on EVERY combat chip, damage number, combo tag, and UI element per frame, forcing offscreen compositing passes on mobile. The top 3 offenders: (1) per-hit damage numbers (WAAPI translate + scale + opacity, ~40–60 concurrent at peak), (2) enemy/hero chip flashes (WAAPI filter animations on every landed hit, ~20–40×/fight), and (3) CSS drop-shadow on combat sprites (a static filter, but present on every chip + every floating element — ~10–20 composited layers per frame). Cut the per-hit WAAPI churn (pool + batch damage numbers, switch chip flashes to brightness-only or baked sprites) and strip the drop-shadows from high-frequency elements → reclaim ~8–14ms/frame at peak load.

WAAPI Inventory (element.animate() calls)

Top Cuts by ROI (Return on Investment)

The following optimizations are ranked by expected frame-time win (how many ms/frame you reclaim at peak load) vs. feel cost (what the player loses). Each includes a ready-to-paste follow-up prompt to implement the fix.

1. Pool + batch damage numbers → ~5–8ms/frame win

Suspect: FxLayer.jsx:366–374 — spawnNumber() creates + animates + removes a DOM <div class="dmg"> for EVERY landed hit. At peak load (40–60 concurrent damage numbers), that's 40–60 WAAPI instances + 40–60 DOM nodes churning per second.
Evidence: WAAPI count peaks at 154; damage numbers contribute ~28% (40–60 concurrent). Each number is a fresh document.createElement('div') + .animate() + onfinish = () => d.remove().
Win: Pool 60 <div class="dmg"> nodes (reuse instead of create/remove), batch updates into a single rAF callback (instead of per-hit WAAPI), and composite them via a single translate3d + opacity update per frame. Estimated win: 5–8ms/frame at peak load.
Feel cost: ZERO — the visual is identical (same translate + opacity curve), just batched into fewer WAAPI instances.

Out-of-Scope Flags (non-render-bound)

The following patterns were noted but are outside the VFX render-cost scope (they're simulation or GC issues, not render). Refer to the named specialist agent for each.

  • GC spikes (55–92ms pauses): Occasional 55–92ms hitches visible in the on-device profile — likely major GC triggered by per-tick allocation churn. Not a render issue — this is JS GC tuning. → Refer to slowdown-detective (holistic performance) or gameplay-systems-agent (sim-side allocation patterns).
  • DOM node churn (480→689): Transient damage numbers / combo tags / rings are created + removed per event. The damage-number pool (Cut #1) will reduce this, but the root cause is the DOM-VFX architecture (each effect is a fresh node). This is already flagged in Cut #1.
  • rAF capped at 60fps: The device is capped at 60fps (17ms/frame budget), so the median 17.0ms means the game is hitting the cap — the tail (p95–p99) is where it drops. Not a render issue — the cap is a WKWebView/iOS limit, not a rendering bottleneck.
